## 2 · Streaming: the design decision, and how it was kept safe

The 09-22 handover asked for chatbot-style streaming and named the tension
honestly: `Grounding.repair` runs on the *finished* text, so a streamed prefix is a
claim the database has not vouched for yet. Streaming raw output straight in would
contradict "never invent indicator data".

**Decision (user-selected):** stream into a visibly **draft** style, then swap in
the verified text.

That decision is enforced in the type system, not by convention:

* `AuguryUiState.storyDraft` is a **separate field** from `AuguryUiState.story`.
  `StoryScreen` renders `story` as the verified answer and `storyDraft` only inside
  a card labelled `WRITING…` with the line *"Not checked against the database yet."*
  A draft is therefore structurally unable to render as the reading.
* `AuguryGateway.storyStream(...)` returns the **grounded** `StoryResult`, and has a
  default implementation that simply calls `story()` — so a gateway with no model
  (or a real install whose GGUF is missing) satisfies the same contract and never
  calls back.
* The draft arrives on the gateway's IO thread while the user can still navigate.
  `AuguryViewModel` guards it with a `storyRequest` id: `back()` bumps the id, the
  callback returns `false`, and a late piece cannot write into the next screen's
  state.

### 2.1 · What was built

| Layer | Change |
|---|---|
| `augury_engine.{h,cpp}` | `TokenCallback` + `generate_stream(...)`; `generate()` is now a thin wrapper over one shared `run_turn` body, so the two entry points cannot drift |
| `augury_jni.cpp` | `nativeGenerateStream(..., sink)` — resolves `boolean onPiece(String)` once, calls it per piece on the generation thread (no `AttachCurrentThread` needed), propagates a sink exception instead of swallowing it |
| `LlamaEngine.kt` | `fun interface TokenSink`, `generateStream(..., onDelta)` |
| `AuguryGateway.kt` | `storyStream(...)` with a no-model default |
| `AuguryGatewayImpl.kt` | `generateDraftStreaming`, and a shared `buildStory`/`formatterPrompt` so the streamed and blocking paths ground identically |
| `AuguryViewModel.kt` | draft accumulation, `streaming`, `storyKey`/`storyDisplayName`, cancellation |
| `StoryScreen.kt` | the `WRITING…` draft block, and a title that no longer flickers |
| `DemoGateway.kt` | simulated stream, so the draft→swap is reviewable with no device |

`generate()` was deliberately **kept**: it is the path `OnDevicePipelineTest`
already measures, and keeping it makes the host test a true A/B parity check.

### 2.2 · The evidence

**Host, against the real 688 MB GGUF** (`tools/host_test.cpp`, ~2 s):

```
stream_pieces    : 40
stream_chars     : 160
stream_ms        : 1905
```

and the assertions that matter: the concatenated pieces equal the returned text
**exactly**, the callback's early stop stops it at 40, and the streamed prefix is a
prefix of what `generate()` produces for the same prompt.

**Device** (`OnDeviceStreamTest`, `OK (2 tests) in 30.7 s`):

```
stream: pieces=48 chars=206 first_piece_ms=8998 total_ms=23091
stream stats: load_ms=272;prompt_tokens=174;prompt_ms=8713;gen_tokens=48;
              gen_ms=14093;tokens_per_sec=3.406;n_ctx=2048;n_threads=4
stream early stop: pieces=3 chars=12
```

The 8,998 ms is **prompt evaluation** (8,713 ms of it is `prompt_ms`), which is why
the screen has two waiting states: *"Reading the database…"* before the first
token, *"Writing…"* after it.

**Through the app's own UI**, mid-turn:

```
"Button grass"  /  "Dactyloctenium radulans · Australia"
WRITING…
  " alkaline"                                  ← draft, dimmed italic
  "Not checked against the database yet. The verified reading
   replaces this as soon as the writer finishes."
```

and when the turn landed the draft block was gone, replaced by the grounded
reading, its 6 database indicator rows and the provenance card.

> The draft block showed `" alkaline"` — a raw token piece with a leading space.
> `trimStart()` now fixes that. Found by looking at the screen, not by a test.

## 3 · The grounding-repair path has now fired

The 09-22 handover's open item: *"Every recorded draft was clean (`repairs=0`), so
the Story screen's CORRECTED card has never rendered a genuine model
hallucination."*

`OnDeviceGroundingRepairTest` (4 tests, `OK` in 44.3 s) replays **the text the real
GGUF produced on the host** — not a fixture invented for the occasion — through the
device's own gateway:

```
grounding fixture check: facts contain no '6.5'
grounding repair fired: action=neutralised removed=[6.5] chars=322
grounding repair: action=neutralised removed=[6.5]
  before='The pH picture: Dandelion indicates acidic conditions, likely below 6.5.'
  after ='The pH picture: Dandelion indicates acidic conditions.'
```

The test **first asserts that `6.5` is absent from the shipped facts**, so if the
database ever gains that number the fixture stops being a hallucination and the
test fails loudly rather than passing vacuously. It also asserts the *opposite*
direction — a clean draft comes through byte-for-byte with zero repairs — because a
repair pass that fired on everything would pass the first test while silently
mangling good answers.

## 4 · Tests: 181 → 191

| Test | What it pins |
|---|---|
| `StoryStreamTest` (4) | pieces are a growing prefix; the last piece **is** the story; streaming returns exactly what `story()` returns; a no-model gateway never calls back |
| `AuguryViewModelStreamTest` (6) | a piece sets `storyDraft` but **not** `story`; completion clears the draft; `back()` invalidates a mid-stream turn; a failed turn leaves no draft |
| `OnDeviceStreamTest` (2) | the JNI lookup resolves; the first piece lands at 39% of the turn; concatenation == returned text; early stop keeps the prefix |
| `OnDeviceGroundingRepairTest` (4) | the real hallucination is neutralised on device; a clean draft is untouched; every repair action is one the card can render; device parity with the recorded Python behaviour |

`kotlinx-coroutines-test:1.9.0` was added as a **test-only** dependency: the
streaming state machine lives behind `viewModelScope` (`Dispatchers.Main`), and
without a test dispatcher the part that cannot be exercised by a screen test would
also be untestable on the host.

### 4.1 · Two bugs the tests caught in this session's own work

1. **The host harness double-accumulated the stream.** The callback appended each
   piece *and* `generate_stream` appended it, so the parity check compared 320
   bytes against 160 and failed. The engine was correct; the test was not. Fixed,
   and the harness now says so in a comment.
2. **`DemoGateway.storyStream` ignored its early-stop contract**, emitting the full
   text after the caller had stopped and returning the whole story. It now builds
   the result from the prefix that was actually produced — matching what the real
   gateway does with a truncated draft.

Both are the same lesson as the 09-22 handover's, one layer down again: *the test
is also code, and a test that cannot fail proves nothing.*

## 5 · Open work, in priority order

### 5.0 · The target phone is a CMF Phone 1 — **not** the A10s

The 09-22 handover documented a **Samsung Galaxy A10s (SM-A105)** as the loop's
real device. That was a miscommunication: the phone in play is a **CMF Phone 1**
(`A015`, CMF by Nothing). This matters more than a name, because the A10s's
geometry was used to justify a layout decision.

| | A10s (what the docs assumed) | **CMF Phone 1 (actual)** |
|---|---|---|
| Display | 720×1520 | **1080×2400** |
| Density | 280 dpi | ~395 dpi *(computed; not measured on the device)* |
| Width in dp | 411 dp | **~437 dp** |
| SoC | Helio P22, 8×A53 | **MediaTek Dimensity 7300**, 4×A78 @2.5 GHz + 4×A55 |
| RAM | 2 GB | **8 GB** (+8 GB virtual) |
| Storage | 32 GB | 128 GB UFS 2.2 |
| Android | 9 | **14** with Nothing OS 2.6 (Android 15 / Nothing OS 3.0 after update) |
| ABI | arm64-v8a | arm64-v8a |
| Battery | 4000 mAh | 5000 mAh, 33 W |

Sources: [CMF Phone 1 specs](https://www.fonearena.com/blog/428132/cmf-phone-1-price-india-specifications.html/amp),
[Nothing's product page](https://us.nothing.tech/products/cmf-phone-1).

**What this changes:**

* **The layout audit needs redoing on the phone.** 09-22 §3.5 argued the fault was
  device-independent *because* the A10s was 411 dp wide — exactly the emulator's
  width. The CMF Phone 1 is **~437 dp**, so that argument no longer holds, and the
  "no overlapping text on any screen" result is only established at 411 dp and
  1.3× font. It is very likely still fine (a wider screen wraps *less*), but
  "likely" is not the standard this project has been holding itself to.
* **The memory worry is gone.** 09-22 §7 worried a 2 GB A10s would be tight for
  the ~1.25 GB photo path. At 8 GB there is real headroom.
* **The APK is unchanged** — both phones are arm64-v8a, so the same
  `app-arm64-v8a-debug.apk` installs on either.
* **Nothing OS is not stock Android.** `ACCESS_NETWORK_STATE` / metered-connection
  detection is the piece most likely to behave differently, and the Wi-Fi-only
  gate depends on it. Worth checking on first launch.

### P0 — measure on the physical phone
Everything here is emulator numbers. Wanted, in rough order of value:

1. **Prompt evaluation time** — it dominates streaming latency (8.7 s of the
   emulator's 9.0 s to first token). This is the number that decides whether the
   `WRITING…` state is a brief pause or a long stare.
2. **tokens/sec** — the emulator measures 3.4; a Dimensity 7300 with 4 big cores
   should be meaningfully faster, which is also the point at which per-token
   `_state.update` should be re-examined.
3. **ONNX load time and a real memory profile** for the photo path.
4. **The layout audit** at the phone's own geometry, per §5.0.

Verified in the artifact, not assumed: `lib/arm64-v8a/libaugury_llama.so` exports
`Java_au_org_regeneratus_augury_LlamaEngine_nativeGenerateStream`, so this build
contains the streaming path.

```bash
adb install -r .dsh-runtime/dist/augury-0.1.0-arm64-debug.apk
```

Notes for the phone:

* **`-r` keeps the ~1.06 GB download** if the previous install came from the
  sandbox build path. If it came from the plugin's `android_build_run`, the debug
  keystores differ and the install fails with `INSTALL_FAILED_UPDATE_INCOMPATIBLE`;
  `adb uninstall au.org.regeneratus.augury` first, and the download starts over.
* **Use the arm64 split, never the universal or x86_64 one.** The universal APK is
  99 MB for no benefit; the x86_64 one fails as "App not installed".
* First launch is the full 1.06 GB download, Wi-Fi-only by default.
* To watch the streaming behaviour: open a species with indicators (Dandelion is a
  good one), then watch for *"Reading the database…"* → **`WRITING…`** with dimmed
  italic text → the grounded reading replacing it. The draft block is the thing
  this build adds.

## 7 · Host caveats worth not rediscovering

* **Never drive the UI while `am instrument` is running.** `monkey`'s force-stop
  kills the instrumentation process and `am instrument` reports it as
  **"Process crashed"** with an empty crash buffer. It looks exactly like an app
  crash. This session lost a test run to it.
* `adb` is not on `PATH` here; it lives at `$ANDROID_HOME/platform-tools/adb`.
  The `android_*` tools find it themselves, so this only matters when a shell
  command needs it directly.
* `android_tap_element`'s `label` matches **text or content-desc**, and a substring
  match on `"Dandelion"` hits the *search field* before the suggestion row. Use
  `android_ui_rows` + `android_tap_row`, or coordinates read from a fresh tree.
* The emulator renders slowly enough that a token-by-token `_state.update` is fine
  (~3.4 tokens/sec); this is **not** evidence that per-token state updates would be
  acceptable at phone speed. Revisit if the phone measures much higher.
* `android_ui_tree`'s `filter` is a plain substring. Two concurrent calls on one
  device can kill each other's uiautomator dump — go sequentially.
