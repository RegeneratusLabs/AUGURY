## 2 · The headline: it runs, and first launch now works

Earlier in this session nobody had seen this app execute. It now runs, and the
download phase — the part that was broken — works end to end.

### 2.1 The bug that blocked first launch

**Symptom.** First launch, tap *Continue*: **"Story writer" failed instantly**
(`failed — tap to retry`), the other three artifacts stayed `queued`, the
staging directory was empty, and **logcat said nothing at all**.

**Root cause.** An artifact's Hugging Face **repo kind** was not part of the
manifest, so `ArtifactManager` used one repo type (`source.repoType`, default
`DATASET`) for every artifact. But the artifacts do not live in one kind of repo:

| Artifact | Repo | Kind |
|---|---|---|
| formatter GGUF | `RegeneratusLabs/augury-1b` | **model** |
| species DB, encoder | `RegeneratusLabs/augury-app` | dataset |
| vision index | `RegeneratusLabs/augury-vision-index` | dataset |

Hugging Face resolves those with **different URL prefixes**:

```
/datasets/RegeneratusLabs/augury-1b/resolve/<rev>/MiniCPM5-...gguf      -> 401  ✗
/RegeneratusLabs/augury-1b/resolve/<rev>/MiniCPM5-...gguf               -> 200  ✓
/datasets/RegeneratusLabs/augury-app/resolve/<rev>/augury-ondevice.json -> 200  ✓
/models/RegeneratusLabs/augury-1b/resolve/<rev>/...                     -> 404  ✗
```

So the very first artifact (the 688 MB GGUF, deliberately installed first) 401'd
and aborted the whole install.

**A second, latent bug sat next to it:** `HuggingFaceRepoType.MODEL` was declared
as `segment = "models"`, but model repos have **no prefix at all** —
`/models/<repo>/resolve/...` is a 404. Fixing only the first bug would have
turned a 401 into a 404.

**The fix (data-driven, per the architecture):**

| File | Change |
|---|---|
| `artifacts/Http.kt` | `HuggingFaceRepoType.MODEL.segment` is now `""`; `resolve()` omits the slash; added `fromManifest()` |
| `artifacts/ArtifactManifest.kt` | `ArtifactSpec` gains `repoType`; `parseSpec` reads `repo_type` (absent ⇒ `dataset`, so older manifests still work) |
| `artifacts/ArtifactManager.kt` | resolves each artifact with `spec.repoType` |
| `scripts/app/build_ondevice_bundle.py` | emits `repo_type` on all four specs (`model` for the GGUF) |
| `data/app/manifest.json` | patched live, digest recomputed, **republished** |
| `ManifestSourceTest.kt` | had **asserted the broken URLs** (including the GGUF at a `/datasets/` path) — corrected against the live service |

> **Why 162 green tests did not catch this.** `ManifestSourceTest` tested
> `HuggingFaceUrls.resolve` with a hard-coded `DATASET` argument for the
> formatter repo, and asserted `/models/...` for a model repo. The tests encoded
> the bug as the expectation. **The lesson worth carrying:** a unit test that
> pins a URL is only as good as the URL someone verified against the real
> service.

### 2.2 The second bug the device exposed: window insets

`MainActivity` calls `enableEdgeToEdge()`, so the app draws under the system
bars — but **no screen applied window-inset padding**. The pinned footer
therefore sat *underneath* the navigation bar:

| | Before | After |
|---|---|---|
| content view | `y:0 h:2400` | `y:128 h:2146` |
| footer button | `y:2237–2368` | `y:2111–2242` |
| nav bar | `y:2274–2400` | `y:2274–2400` |
| button centre | **y=2303 → swallowed** ✗ | **y=2180 → clear** ✓ |

*Start identifying* was untappable at its centre and silently did nothing.
Fixed with `.windowInsetsPadding(WindowInsets.safeDrawing)` in `ScreenScaffold`,
so every screen inherits it.

"failed" and the exception was swallowed by a `runCatching`, which is why this
took a device and a `run-as` inspection of the filesystem to diagnose.

## 4 · How to run the app on a device (the working loop)

The DSH Android plugin (`@zseven-w/dsh-android`) is the mechanism. It runs
**in the DSH host process**, which is outside the agent sandbox and therefore
has real `/dev/kvm`.

```
android_devices            → lists devices + bootable AVDs (currently: InvoiceYarn_Test)
android_boot   <AVD name>  → boots and streams it (emulator-5554, Android 14)
android_launch_app         → packageName: au.org.regeneratus.augury
android_ui_tree            → THE observer on this host (see caveat below)
android_screenshot         → for the human
android_logs               → filter by bundle_id; tag "AuguryGateway" for download errors
android_shutdown           → emulators only
```

**Caveats that will save time tomorrow:**

1. **OCR is unavailable on this host.** `android_find_text` / `android_tap_text` /
   `android_wait_for` need Apple's Vision framework (macOS). This is Linux, so
   **use `android_ui_tree` + `android_tap_element`** and verify by re-reading the
   tree. Do not pass `expect_text` to the tap tools — it fails with the OCR error
   *before* tapping.
2. **`android_ui_tree`'s `filter` is a case-insensitive substring, not a regex.**
   A pattern like `"soil|Search|photo"` matches literally and returns nothing.
3. **The emulator's AVD `augury` is not the one the plugin sees.** The plugin
   lists AVDs from the host AVD home (`InvoiceYarn_Test`). The `augury` AVD lives
   in the workspace runtime dir and is only reachable by the sandbox's own adb.
4. **`android_build_run` currently fails on this project.** It returns a
   truncated Gradle trace with no actionable error. The reliable path is: build
   in the sandbox, then install with adb directly:
   ```bash
   # build (sandbox, needs the env shim)
   cd augury-android && source scripts/spike-env.sh
   ./gradlew :app:assembleDebug            # → app/build/outputs/apk/debug/
   # install (the sandbox adb CAN reach the emulator; it just needs a writable HOME)
   export HOME=$PWD/.dsh-runtime/home TMPDIR=$PWD/.dsh-runtime/tmp
   $ANDROID_HOME/platform-tools/adb -s emulator-5554 install -r -t \
     app/build/outputs/apk/debug/app-x86_64-debug.apk
   ```
   `pm clear au.org.regeneratus.augury` resets to a true first-launch state.
5. **Use the x86_64 APK on the emulator.** ABI splits mean the arm64 APK will not
   install on an x86_64 emulator. (Sideload `app-arm64-v8a-debug.apk`, 48 MB, on a
   phone.)
6. **Run Gradle builds one at a time.** `gradle.properties` caps the heap at 3 GB.

## 5 · Why the emulator took so long — recorded so it is not repeated

**The sandbox cannot see `/dev/kvm`.** The agent sandbox is a `bwrap` namespace
(`--ro-bind / /` plus selective writable binds); `mknod` is blocked by
no-new-privileges. Android's x86_64 emulator hard-requires KVM, so inside the
sandbox it refuses to start.

**Docker solves the KVM half but not the emulator half.** `docker run --device
/dev/kvm` genuinely works — `-accel-check` reports
`KVM (version 12) is installed and usable` — but the emulator then **SIGSEGVs
~35 s into every boot**, inside its own bundled SwiftShader:

```
Thread "RenderThread" received signal SIGSEGV
#1 .../emulator/lib64/gles_swiftshader/libGLESv2.so
```

Recorded in `augury-android/scripts/emulator-in-docker.sh` (kept as an
investigation record, marked as not working). Obstacles worked around and
verified along the way: `/home` is `ro,nosuid,nodev` at the filesystem level
(so the SDK is streamed into a Docker **named volume** rather than bind-mounted),
Docker's buildx needs a writable `$HOME`, and a killed emulator leaves AVD lock
files that cause `Running multiple emulators with the same AVD`.

**It is NOT a security policy.** Ruled out with evidence:

| Candidate | Finding |
|---|---|
| SELinux | **`Disabled`** on this host |
| AppArmor | **module not present** |
| Docker seccomp | `--security-opt seccomp=unconfined` → still SIGSEGV |
| Capabilities | `--privileged` → still SIGSEGV |
| GPU mode | `-gpu off`, `guest`, `swiftshader_indirect`, and `hw.gpu.enabled=no` → all still load `libGLESv2` and all still crash |

**Also corrected from the 09-19 handover:** its "run QEMU directly" workaround
was based on a misreading. In emulator 36.x,
`emulator/qemu/linux-x86_64/qemu-system-x86_64-headless` **is the emulator**
(its `-help` lists `-avd`, `-radio`, `-dpi-device`), not raw QEMU — so it rejects
QEMU flags like `-device` with `unknown option: -device`. There is no
separately-drivable QEMU anymore.

**Therefore: use the dsh-android plugin.** It launches the emulator from outside
the sandbox and it works.

| `MiniCPM5-1B-AUGURY-Q4_K_M.gguf` | `augury-1b` (**model**) | `342d62ab82a9` | 688,065,824 |

Manifest `generation` is now `81e85f0815746fb4…` (it moved when `repo_type` was
added). Bands `auto 0.64 / confirm 0.30`; index `16,580 × 384`, 173 species.

**Publish gotchas (these cost real time):**

- **`HF_TOKEN` must be exported explicitly.** `$HOME` is read-only here, so
  `HF_HOME` is redirected — and that redirect also redirects the *token lookup*,
  which makes every call fail auth with a misleading "repo not found".
  ```bash
  export HF_HOME="$PWD/.dsh-runtime/hf-home" HF_HUB_DISABLE_XET=1
  export HF_TOKEN="$(cat ~/.cache/huggingface/token | tr -d '\n')"
  ```
- **Xet must stay disabled** (`HF_HUB_DISABLE_XET=1`): its staging dir lands on
  the read-only mount.
- **`build_ondevice_bundle.py` rewrites `augury-ondevice.json` with a fresh
  `generated` timestamp on every run**, changing its sha256. Either re-upload the
  facts file whenever you regenerate, or — as was done for the `repo_type` fix —
  **patch the live manifest JSON and recompute `generation`** (sha256 of the
  canonical body minus `generation`; `sort_keys=True`, `separators=(",",":")`,
  `ensure_ascii=False`) and upload only the manifest.
- **`generation` is a digest of the manifest body.** Any edit to the manifest
  requires recomputing it, or the app rejects the manifest as inconsistent.

## 7 · Open work, in priority order

### P0 — the photo path has never run
`OnnxEncoder` has **never loaded the 346 MB graph on a device**. The maths is
verified against Python (`VisionParityTest`, 8 tests: preprocessing within the
recorded kernel delta, whitening matches, top-3 identical), but the device-side
surfaces are untested: ORT Mobile loading the `.onnx`, `BitmapFactory` decode
feeding the preprocessor, and peak memory when the encoder is resident. This is
the single largest remaining unknown. Start here tomorrow.

### P0 — the formatter model has never generated a story
The GGUF downloads fine, but `AuguryGatewayImpl.generateDraft()` has **never been
exercised**. Consequences: every story is currently the deterministic template;
the prompt built for the model has never been compared against
`scripts/augury_funnel.py`'s; and the grounding-repair path (the Story screen's
"CORRECTED" card) has never seen a real model draft — the very failure it exists
to catch. Also unverified: that the engine and encoder are never resident
together, and the documented ~1.7 s/answer on a phone.

### P1 — `android_build_run` fails on this project
The plugin's build tool fails with a truncated Gradle trace and no actionable
error. Worth diagnosing (it is the tool you will want for the tight loop), but
the adb path in §4 works today. **Note the host build uses the real `$HOME`**,
so the sandbox's `spike-env.sh` shim is not the issue.

### P1 — species display names on the photo screen
`AuguryGatewayImpl.identify` returns the canonical key as `scientificName` and
leaves `commonName` null, so the confirm card shows `cirsium vulgare` rather than
"Spear thistle". The picker shows proper common names. Fixing this needs a public
display accessor on `SpeciesStore` (its `species` map is private).

### P1 — the confirm step is still unexercised
The top-3 confirm card, the low-confidence branch, and the *"a photo never
silently accepts a species"* rule have only been reviewed in
`docs/ui/mockup.html`. No photo has been run through the app.

### P2 — `docs/vision-kotlin-verification.md` was never written
The fixture generator (`tools/emit_vision_fixtures.py`) and the parity tests
exist and pass; the written record of what was run and what remains unverified
does not. `VisionParityTest`'s class comment documents the method — promote it.

### P2 — release build is not shippable
`release` has `isDebuggable = true` and `isMinifyEnabled = false`, left from the
spike. Needs a keystore, `isDebuggable = false`, and R8 before anyone sideloads
a "real" build.

### P2 — test a physical phone
There is a **Pixel 7 online on Tailscale** (`100.86.170.58`). Wireless debugging
is off, so `adb connect` gets `Connection refused`. Enabling it gives a real
device: real download speeds, real memory pressure, real ONNX performance — and
it is the only way to answer the P0 items honestly. `ADBKeyboard` is needed for
non-ASCII input (the plugin refuses rather than mistyping).

### P3 — UI polish
The Setup screen repeats the ~1.06 GB notice once the download is complete (it is
informational, but reads oddly under "Everything is downloaded"). Cosmetic.
