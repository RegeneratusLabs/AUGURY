## 2 · Bug 1 — "when I go to take another photo, it goes back to the previous weed ID's data"

### 2.1 · Reproduced first, on the emulator

Driven through the real UI, both natural "another photo" actions failed **after a
completed story**:

```
Story screen → "Photo instead"
    Is this your plant?  /  BEST MATCH  /  Prickly acacia · Acacia nilotica 1.00
    footer:  "Yes, this is it — show my soil"   "None of these — search by name"

Home screen → "📷  Take photo"
    …the same stale card.
```

The confirm card offers **no camera and no gallery button** — so once you were on
it, a second photo was unreachable. That is exactly the reported behaviour.

### 2.2 · Cause

`AuguryUiState.photoCandidates` was cleared **only** inside `onPhotoPicked`. Every
"take a photo" affordance was a bare `go(Screen.PHOTO)`, which navigates without
touching the session, so the previous run's candidates were still in state and
`PhotoScreen` rendered its confirm branch. The same gap applied to an in-flight
`identify`: retrieval loads a ~340 MB encoder, so a result could outlive the
screen that asked for it and land in the next session.

### 2.3 · Fix

* **`AuguryViewModel.startPhoto()`** — the single entry point for "take a new
  photo". Resets candidates/empty/unavailable/identifying and the story fields,
  and bumps a new **`photoRequest`** id.
* **`onPhotoPicked`** now captures that id and **drops a result for a photo the
  user has left** — mirroring the `storyRequest` guard the streaming work already
  established, rather than inventing a second pattern.
* **Wired:** Home `📷 Take photo` and Story `Photo instead` both call
  `startPhoto()`.
* **Added:** a `📷 Take another photo` action on the confirm card, so a wrong
  match can be reshot without backing all the way out to Home. *(This is the one
  product-side judgement in this session; it is easy to remove if unwanted.)*

`back()` from the Story screen still returns to the confirm card — that is
standard back behaviour and it is genuinely useful (it is how you switch to a
runner-up) — but that card now has an escape hatch, so it is no longer a trap.

### 2.4 · Evidence after the fix

```
Home → Take photo → Choose from gallery → (new photo)
    Old Man Saltbush  /  Atriplex nummularia  /  ● High confidence  /  1.00
    footer:  "Yes, this is it…"   "📷 Take another photo"   "None of these…"

confirm card → "📷 Take another photo"
    Identify from a photo
    "📷  Take photo"   "Choose from gallery"

…a full story later…  Story → "Photo instead"
    Identify from a photo            ← was the stale Prickly acacia card before
```

A second, different gallery photo identified as a **different species**
(Atriplex, not the earlier Acacia), which is the part "not the new uploaded
image" was about.

## 4 · The held-out success rate — 85.87% top-1

This replaces "the photo path works" with a number.

### 4.1 · Method, and why it is not UI taps

Driving the system photo picker for hundreds of images is not possible: it shows
recents only, and each pick costs ~20 s. So the harness drives **the app's own
real `AuguryGatewayImpl.identify()`** — the same code the confirm card calls, with
the device's downloaded ONNX encoder and shipped index — via instrumentation, and
writes one CSV row per image. Two images were then driven through the **actual UI**
and both matched the harness exactly (§4.5).

### 4.2 · The query set

The held-out AU split (`data/vision/au_split.json`): **920 queries, 173 species,
141.5 MB**. Their paths are **disjoint from the split's own `gallery` lists** —
the gallery the shipped index was built from — so nothing here is memorised. The
offline scorer reports 85.9% top-1 on the same set, which makes the device number
directly comparable.

### 4.3 · Result

```
ACCURACY n=920 answered=920 top1=790 top3=854 auto=582 autoCorrect=554
         top1_pct=85.87 top3_pct=92.83 auto_pct=95.19 secs=526.5 ms_per_image=572
```

| Metric | Result |
|---|---|
| **Top-1** ("Best match") | **790/920 = 85.87%** |
| **Top-3** (right plant on the confirm card) | **854/920 = 92.83%** |
| Right species **absent from all three** | 66/920 = 7.17% |
| AUTO band coverage | 582/920 = 63.26% |
| **AUTO band precision** | **554/582 = 95.19%** (28 wrong) |
| Speed | mean 569 ms · median 557 ms · max 3351 ms (first image = ONNX load) |

**85.87% on the device against the offline 85.9%** — the app reproduces the
offline pipeline essentially exactly. That is the strongest thing this run shows.

### 4.4 · What the misses are

They are overwhelmingly **closely-related grasses, sedges and congener pairs** —
botanically hard, and exactly where a photo-only ID should be humble:

```
2x cirsium arvense        -> cirsium vulgare
2x calamagrostis epigejos -> holcus lanatus
2x lolium perenne         -> elymus repens
2x digitaria sanguinalis  -> digitaria ciliaris
2x anthoxanthum odoratum  -> holcus lanatus
worst: agrostis stolonifera, festuca rubra, anthoxanthum odoratum (1/5 each)
```

Scores separate the two populations cleanly: top-1 score median **0.72 on hits vs
0.54 on misses**. The dangerous case — the app says "High confidence" and is wrong
— is **4.81%**, which is what the mandatory confirm step exists for.

### 4.5 · Through the actual UI

| Image | UI showed | Harness row |
|---|---|---|
| q0001 | **Doublegee / Emex australis 0.63**, "Possible match" | `emex australis` 0.6339, CONFIRM ✅ |
| q0007 | **Chilean needle grass / Nassella neesiana 0.36** | `nassella neesiana` 0.3555, truth `bromus hordeaceus` — a genuine **miss**, rendered honestly |

### 4.6 · Two corrections recorded against this session's own work

1. **The first held-out check was the wrong comparison.** It compared query
   *paths* against index *basenames* and printed "0 of 920" — the right conclusion
   from a test that could not have failed. The real guarantee is path
   disjointness. **72 queries share a basename with an unrelated gallery file**
   (320 basenames repeat in the gallery at large), so a basename test both misses
   real leakage and invents false positives. `prepare_heldout_queries.py` now
   asserts against the split's gallery **paths**.
2. **The harness truncated its own CSV header.** `writeText(header)` followed by
   `bufferedWriter()` (mode `"w"`) wipes the header on the second open. All 920
   rows were intact; the summariser was made tolerant and the test fixed. The
   lesson is the same one 09-23 recorded one layer down: *the test is also code.*

### 4.7 · Caveat that must not be lost

These are **gallery/iNaturalist photos — the distribution the model was calibrated
on**, not photos from a phone camera in a paddock. The emulator camera cannot
produce a weed. **Field accuracy is still unmeasured and will be lower.** What
this run establishes is that the *device* pipeline reproduces the *offline*
pipeline, at scale, on unseen data.

## 5 · The appearance aid — designed, NOT built

The two bugs and the 7% miss rate converge on one user problem: **the app offers
three names and you cannot tell which is your plant.** This session designed the
fix and stopped at the decision, deliberately.

### 5.1 · The evidence reframes it

Re-analysed from the 920 held-out top-3 sets:

* **97.5%** (897/920) of top-3 sets are **mixed-genus** — the three plants are
  visibly different, so layperson-visible features can separate them.
* Only **2.5%** (23/920) are congener sets — *Juncus* effusus/acutus/conglomeratus,
  *Cirsium*, *Rumex*, *Plantago* — where even a botanist needs a key.
* **18 of the 28 AUTO-band errors had the correct plant in the top-3.**

**So this is a safety/UX feature, not an accuracy feature.** It stops wrong
confirmations; it does not raise the model's accuracy much (≈12 cases/920 where
the truth was offered and a sibling outranked it).

### 5.2 · What does not exist

**No plant-appearance data exists anywhere in the repo.** The shipped DB carries
only `key / common_name / scientific_name / specificity / has_indicators /
regions.indicators`; `inat_taxa_cache.json` holds taxon **ids only**. Any
appearance aid therefore needs a **new, authored dataset** — that dataset, not the
code, is the real cost.

### 5.3 · The licensing rule eliminates the easy sources

The project's rule is **MIT/Apache/CC-BY only**. The vision gallery is
**CC-BY-NC aggregate** (iNat) and Wikipedia text is **CC-BY-SA** (copyleft). Both
are out. Any appearance data must be **authored/curated from public-domain or
CC-BY sources and released CC-BY-4.0**, exactly like the existing indicator DB.
LLM-generated traits are forbidden by "the model never generates facts".

### 5.4 · Options and verdicts

| Option | Verdict |
|---|---|
| **Show the user's own photo** on the confirm card | **Do first.** The app currently discards the photo and shows **no image at all**. Zero new data, zero new dependency (`Image(bitmap.asImageBitmap())`). |
| **Structured traits + automatic differential** | **Recommended core.** Show only the traits that *differ* among the three. Deterministic, cheap, testable, reusable. |
| Small fixed icon set (leaf shapes, flower forms) | **Keep.** Drawn as Compose vector paths — no assets, no new dependency. |
| Per-species SVG drawings | **Reject.** 173–2,256 hand-drawn species illustrations; doubtful accuracy; "images in another format"; anything traced from the gallery inherits **NC**. |
| Reference photos of the candidates | **Reject.** Size, plus the NC licence. |
| Offer candidates 4–10 / "none of these" | **Cheap add-on.** `VisionSettings.REQUIRED_TOP_K = 3` is a floor; kNN can return more. Attacks part of the 7.17%. |
| Multi-photo disambiguation | **Measure first.** Data-free; targets the congener cases traits cannot fix. The held-out set has 5 images/species, so averaging k=2–3 embeddings and re-checking top-1 is a cheap offline experiment. |

### 5.5 · Recommended shape (for the next session)

* **Phase 0 (no new data):** show the user's photo; better "photograph the flower
  head / leaf base" copy; expand candidates on demand; run the multi-photo
  experiment.
* **Phase 1:** curated, sourced, **layperson-observable** traits for the **173
  species the photo path can return**; a **"Tell them apart"** block showing only
  the differing traits; an **honest fallback** when nothing differs (*"These three
  look alike from a photo — try a close-up of the flower head"*).
* **Phase 2:** trait filter on the picker; "what it looks like" on the story
  screen.

**Design principles:** traits must be **visible to a non-expert holding the
plant** (flower colour/form, leaf shape, habit, spines, size, smell) — not key
characters like ligule shape; the vocabulary must be **closed** so a differential
is computable; the confirm rule stands.

### 5.6 · The open decision

**Invest in curating ~8 traits × 173 species** from public-domain/CC-BY sources,
released CC-BY-4.0? That curation — a few days of human work, reviewable, with a
source per value — is the feature. The code is small; the dataset is the project.

## 9 · Host caveats worth not rediscovering

* **`adb root` works on `augury-api34`** and was required to stage files. It
  restarts adbd; the device stream reconnects on its own.
* **API 34 blocks `adb shell` from creating directories under
  `/sdcard/Android/data/<pkg>`**, and the app cannot traverse an external
  directory that root created. Stage harness data into the app's **internal
  `filesDir`** and `chown -R` it to the app's UID (`stat -c %u /data/data/<pkg>`).
* **Each `bash` call gets a fresh `/tmp`** — a file pulled to `/tmp` in one call
  is gone in the next. Use a workspace path (`.dsh-runtime/tmp/`).
* **`bash` calls are killed at a 60 s default.** Long waits and `am instrument`
  belong in background jobs.
* **Never drive the UI while `am instrument` is running** (09-23's caveat,
  re-confirmed). It looks exactly like an app crash.
* **`writeText(header)` then `bufferedWriter()` truncates the header** — open
  once, or write the header through the same writer.
* **Compare held-out sets by path, never by basename** (72 collisions here).
* `android_tap_element`'s `expect_text`/`expect_gone` and the OCR trio need
  Apple's Vision framework, so on this Linux host they fail by design — observe
  with `android_ui_tree` and confirm by re-reading it, sequentially.
