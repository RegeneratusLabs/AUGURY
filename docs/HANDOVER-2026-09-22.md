## 2 · AUGURY has its own AVD

`InvoiceYarn_Test` was never this project's device: it points at a Pixel 6 AVD
configured with 2048 MB RAM and a 228 MB heap, which is not enough to hold a
346 MB fp32 ONNX session plus a 688 MB GGUF.

`augury-api34` is AUGURY's own:

| Setting | Value | Why |
|---|---|---|
| `hw.ramSize` | 3072 | the encoder alone adds ~300 MB to the process |
| `vm.heapSize` | 512 | the bitmap decode lives on the Java heap |
| `hw.keyboard` | yes | `input text` needs it |
| `hw.gpu.mode` | host | `swiftshader_indirect` is the mode that SIGSEGVs |
| `fastboot.forceColdBoot` | yes | never inherit a stale snapshot |
| `hw.camera.back` | virtualscene | so the camera path can launch |

The AVD lives inside the project at `.dsh-runtime/avd/augury-api34.avd`
(gitignored), with **one bridge file outside the workspace** —
`~/.android/avd/augury-api34.ini` — because the dsh-android plugin discovers AVDs
only through `emulator -list-avds` against the host AVD home. That three-line file
contains nothing but the absolute path to the workspace AVD.

`android_devices` therefore lists both AVDs; **boot `augury-api34`**.

*Alternative with no file outside the workspace:* restart `dsh web` with
`ANDROID_AVD_HOME=<repo-root>/.dsh-runtime/avd` exported, and the plugin will list
only AUGURY's AVDs.

## 3 · What was actually run

### 3.1 · The photo path (first execution, ever)

`OnDevicePipelineTest` drives the real `AuguryGatewayImpl` on the device with the
artifacts the app downloaded and promoted. Its 12 samples are gallery photos whose
rows are *in* the shipped index, selected by
`augury-android/tools/select_device_vision_samples.py` from the row-aligned
`keys.json`/`files.json`, so their reference embeddings are in `embeddings.npy`.

```
photo path: top1=12/12 top3=12/12 named=12/12 pss 950089kB -> 1252739kB
```

`OK (4 tests)` in 58.0 s on `emulator-5554`. The confirm card's display name is
resolved on the device too, from the species database rather than the index key:
*Prickly acacia*, *Hare's tail grass*, *Athel pine*, and for species with no
vernacular name the database's own binomial spelling.

### 3.2 · The decode bound, measured not assumed

A full-resolution decode of a 12 MP photo spends ~130 MB of heap to feed a 256-px
resize. `DecodeBounds` now bounds it. The device test measures the bound against
the real graph with the full-resolution decode as the control:

```
decode parity: full=acacia nilotica@0.9532776 bounded=acacia nilotica@0.95218736
```

Same top-1, same ordering, score moved 0.0011. Android only honours power-of-two
subsampling, so the bound does not grow with the camera: a 48 MP photo decodes to
the same size as a 12 MP one.

### 3.3 · The formatter (first execution, ever)

```
story: usedModel=true repairs=0 chars=408 pss 930057kB -> 589776kB
```

`usedModel=true` is the load-bearing value: it is false whenever the model could
not be loaded and the deterministic template stood in. The PSS drop is the
co-residency constraint made observable.

The same path through the app's own UI, read from logcat:

```
formatter draft for 'taraxacum officinale': load=585ms total=43700ms chars=255
  :: prompt_tokens=184;prompt_ms=9916;gen_tokens=65;gen_ms=33188;
     tokens_per_sec=1.959;template=embedded-chat-template;n_ctx=2048;n_threads=4
```

That is **emulator** throughput, not a phone measurement. Note `prompt_ms≈10,000`:
the model spends ~10 s reading the prompt *before* the first token, which matters
for the streaming request in §8.

### 3.4 · The photo confirm card, through the UI

A gallery photo pushed to the device and picked through the system photo picker
produced the confirm card: **"Prickly acacia"** / *Acacia nilotica* / "High
confidence" / 1.00, with look-alike rows (Parthenium weed 0.35, Lantana 0.26).
Tapping *"Yes, this is it — show my soil"* then produced the story, so the whole
photo → confirm → story chain has now been watched end to end.

### 3.5 · The layout audit — what the real-phone feedback produced

The first real-device feedback was that text clashed with text: on the download
screen "Downloading" was overprinted by "Story writer", the overall progress bar
ran through its own labels, and the photo screen had the same problem.

**Reproduced, not guessed.** The A10s is 720×1520 at density 280, which is
**411 dp wide — exactly the emulator's width** (1080×2400 at 420). So the fault was
device-independent; the emulator had been showing it all along and it had been read
as cosmetic. The emulator was set to `wm size 720x1520` / `wm density 280` anyway,
and the whole app audited there and again at `font_scale 1.3`.

**Audited mechanically.** `augury-android/tools/check_screen_overlaps.py` reads a
uiautomator dump and reports any two text-bearing nodes whose bounds intersect,
skipping only genuine XML ancestors (geometric containment is *not* enough — a
short label inside a tall paragraph is the bug being hunted). Before and after, on
the same screen:

```
OLD: paragraph at y 218-388            (no label node at all — it was covered)
NEW: 'WHAT WORKS' at y 218-257, paragraph pushed to y 271-441
```

Result: **no overlapping text on any of the six screens** — Setup (queued,
downloading and ready), Home, Picker, Photo (empty and confirm card), Story,
Settings — at both font scales. Sample of the fixed Setup screen while
downloading:

```
y 218-257  'DOWNLOADING'
y 279-318  'Story writer'          x 548-649 'downloading'
y 353-392  '32.3 MB of 688.1 MB'   x 543-663 '4% · 1.7 MB/s'
y 1019-1058 'OVERALL'              x 626-663 '37%'
y 1096-1135 '394.7 MB of 1.06 GB'  x 564-663 'in progress'
```

The download was also re-run from `pm clear` to audit those states, which
re-verified the whole 1.06 GB path and the live progress poller (watched
32 MB → 395 MB on screen rather than frozen at zero).

## 4 · The bug the device found

First device run, every photo test failed with:

```
The image recogniser could not be loaded: manifest vision.preprocess is missing
```

`AuguryGatewayImpl.visionPipeline()` hand-built the preprocessing block and got
**two things wrong at once**:

1. `PreprocessSettings.fromManifest` takes the `vision` block and reads
   `vision["preprocess"]`; the gateway passed the inner block.
2. `VisionJson.num` accepted only a `Double`, while the typed manifest carries
   `Int` — so the values would have failed even with the wrapper right.

Nothing on the host could see it: ONNX Runtime Mobile ships Android libraries, so
no JVM test can construct the pipeline. The mapping now lives in the pure function
`visionPreprocessBlock`, and `VisionManifestBridgeTest` compares it against the
**reference parse of the shipped manifest** on the host. `VisionJson.num` accepts
any `Number`.

**The generalisable part:** the 09-20 handover's lesson — *a unit test that pins a
value is only as good as the path it exercises* — applied one layer down. 162
green tests could not tell whether the pipeline could be built at all.

### 5.1 · The card container bug

**Cause.** `AuguryCard` wrapped its content in a **`Box`**. A `Box` stacks every
child at the same position, and the card sized itself to its tallest child — so a
card written the obvious way was drawn with its section label underneath the
content that followed:

```kotlin
AuguryCard {
    SectionLabel("DOWNLOADING")
    Spacer(Modifier.height(10.dp))
    columnOfArtifactRows()
}
```

Twenty-two call sites, most of them multi-child, so nearly every card in the app
was affected. The `Box` made the mistake silent, and the card's height being the
tallest child's is why the label sometimes vanished from the accessibility tree
entirely rather than merely looking cramped.

**Fix.** `AuguryCard` is a `Column` whose content is a `ColumnScope`, which both
repairs every card at once and makes the mistake unwritable. No caller wanted an
overlay. `SectionLabel` also gained an 8 dp gap before its trailing value, because
a long label and its value were reading as one run of text.

### 5.2 · Two more things the device walk exposed

* **System back exited the app.** From the Story screen, the Android back gesture
  finished the activity and dropped the user on their phone's home screen.
  `BackHandler` now routes it through the app's own navigation, enabled exactly
  where a screen shows its own back arrow: never on Home (the system keeps it and
  the app exits as expected), and not on a Setup that still has work to do.
* **Settings is unreachable.** `SettingsScreen` is complete, and the mockup
  documents it as screen 6, but nothing in the app navigates to it — the only path
  is the automatic "app update required" redirect. It was audited by temporarily
  forcing it as the start screen, then reverting. Adding a Home entry point is an
  open decision (§8), not a bug fix.

## 6 · `android_build_run`: fixed, with one environment caveat

The long-standing failure had a mundane cause: the DSH host process has no
`ANDROID_HOME` and `augury-android/local.properties` was an **empty file**, so AGP
could not locate the SDK and Gradle died with a filtered, unhelpful trace. Writing
`sdk.dir` into that file (gitignored by design) fixes it — `android_build_run` now
**builds the project successfully**.

Its install step then fails with `INSTALL_FAILED_UPDATE_INCOMPATIBLE`, because the
two build paths sign the debug APK with **different debug keystores**:

* the sandbox build uses `$HOME/.android/debug.keystore` with `HOME` redirected to
  `.dsh-runtime/home`;
* the plugin's host build uses the real home's `~/.android/debug.keystore`.

Options: `adb uninstall au.org.regeneratus.augury` once when switching paths
(which discards the ~1.04 GB of downloaded artifacts), or pin a project-owned
debug keystore in `app/build.gradle.kts` so both paths agree. Not done — it means
committing key material.

## 7 · The real-device loop (Samsung A105)

The app is being run on a Samsung A105 (Galaxy A10s) — the first real phone in
this project's loop — and the practical details are worth not rediscovering:

* **Geometry:** 720×1520 at density 280 = **411 dp wide**, the same width as the
  emulator. Emulator screenshots are therefore representative for width; what the
  phone adds is real memory, real thermals and real model speed.
* **The APK:** `app-arm64-v8a-debug.apk` (48 MB) is the only split that installs
  on it; `app-x86_64-debug.apk` is emulator-only and fails as "App not installed".
  A staged copy is kept at `.dsh-runtime/dist/augury-0.1.0-arm64-debug.apk`.
* **Signing:** builds from the sandbox all share one debug key, so a new APK
  installs straight over an old one with `adb install -r` and **keeps the 1.06 GB
  download**. Builds from the plugin's host path use a different key (§6).
* **First launch is a ~1.06 GB download**, Wi-Fi-only by default; the app refuses
  to start it on a metered connection unless the user overrides.
* **Memory:** the photo path takes the process to ~1.25 GB while the encoder is
  resident. Comfortable at 3072 MB; a 2 GB A10s variant would be tight.
* **Still unmeasured on the phone:** ONNX load time, tokens/sec, and whether the
  encoder survives a low-RAM kill.

## 8 · Open work, in priority order

### P0 — measure on the physical phone
Everything so far is emulator numbers. The A105 is in play; what is needed is the
ONNX load time, the formatter's tokens/sec, and a real memory profile.

### P1 — stream the story (requested, designed, not built)
The user asked for chatbot-style streaming instead of waiting for the whole
answer. It is possible, and the shape is known:

1. **Native:** `augury_jni.cpp` exposes one blocking
   `nativeGenerate(handle, system, user, temperature, maxTokens) -> String`. The
   engine already decodes token by token internally; add a variant that calls back
   into Kotlin per piece (the callback runs on the calling thread, so no
   `AttachCurrentThread` is needed).
2. **Kotlin:** `LlamaEngine.generateStream(..., onDelta)`, forwarded through the
   gateway, accumulated in `AuguryUiState`, rendered by `StoryScreen`.

**The decision that has to be made first.** `Grounding.repair` runs on the
*finished* text, so streaming raw output briefly shows numbers the database has not
yet vouched for — in tension with "never invent indicator data". The recommended
option is to stream into a visibly **draft** style (dimmed, labelled *writing…*)
and swap in the verified text when it lands, keeping the "corrected" notice if
anything was removed. Streaming straight in as final text feels best but shows
unverified claims.

Also budget the ~10 s of prompt evaluation before the first token (see §3.3); that
part should read as "reading the database…".

### P1 — the grounding-repair path has still never fired
Every recorded draft was clean (`repairs=0`), so the Story screen's "CORRECTED"
card has never rendered a genuine model hallucination. Prompting the model
adversarially, or replaying the funnel's recorded bad drafts through
`Grounding.repair` on device, would close it.

### P1 — held-out photo accuracy was not measured on device
The 12/12 result uses *in-index* rows, so it demonstrates device parity, not
accuracy. The held-out figure (85.9%) comes from the offline calibration.

### P2 — Settings has no entry point (needs a decision)
See §5.2. A gear in the Home header is the obvious fix; it is a design call.

### P2 — the ` thinking` strip is unexercised in practice
Correct and unit-tested, but this model/template emitted no thinking block in any
run.

### P2 — release build is not shippable
`isDebuggable = true`, unminified, unsigned.

### P3 — data polish
The browse list shows "Spear thistle" twice (two database rows), and 60 of the
index's 173 species have no vernacular name, so their card shows the binomial.

**Host caveats worth not rediscovering.** The OCR tools (`android_find_text`,
`android_tap_text`, `android_wait_for`) and the tap tools' `expect_text` need
Apple's Vision framework, so on Linux they fail by design — observe with
`android_ui_tree` and confirm by re-reading it. `android_ui_tree`'s `filter` is a
plain substring, not a regex; a pattern like `"soil|Search"` matches nothing. Two
concurrent `android_ui_tree` calls on one device can kill each other's uiautomator
dump, so go sequentially. And a screen can legitimately lag a tap by a second or
two — the first read after a model-backed action showed the composing state while
the logcat line said the draft had already finished.
